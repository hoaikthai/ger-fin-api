# Security Review — GerFin API

- **Project:** `ger_fin_api` (Go 1.23, Gin, GORM, PostgreSQL, JWT)
- **Review date:** 2026-07-02
- **Reviewer:** Automated source-code security review
- **Commit reviewed:** `69384ef` (branch `master`)
- **Scope:** Full application source under `internal/` and `cmd/`. Static source review only — no running instance or dynamic scanning.

---

## Executive Summary

The codebase is in good shape on the highest-risk fundamentals. All database access uses parameterized queries or GORM placeholders, so there is **no SQL injection**. Passwords are hashed with bcrypt and never serialized (`json:"-"`). Per-user data access is consistently scoped to the authenticated `userId` across accounts, transactions, categories, budgets, and reports, so there is **no broad IDOR / cross-tenant data leak** in the CRUD paths.

The findings below are hardening and access-control gaps rather than critical breaks. The most notable is a missing ownership check on the CSV import-job status endpoint (H-1) and the absence of authentication rate limiting (H-2), which together with account enumeration (M-3) weakens the auth surface against automated attacks.

| ID | Severity | Title |
|------|----------|-------|
| H-1 | High | CSV import-job status endpoint lacks ownership check (IDOR) |
| H-2 | High | No rate limiting on authentication endpoints (brute force / credential stuffing) |

## Methodology

- Enumerated all Go source, config, migration, and environment files.
- Reviewed the authentication and authorization layer (`internal/auth`, `internal/middleware`, `internal/common/jwt.go`).
- Audited every service for SQL construction, tenant scoping, and raw-error exposure.
- Reviewed HTTP handlers for input validation, IDOR, file-upload handling, and information disclosure.
- Checked configuration and secret handling (`internal/config`, `.gitignore`, DSN construction).

Confirmed non-issues:
- **SQL injection:** every query uses `?` placeholders or GORM argument binding; dynamic query assembly in `budget/service.go` and `report/service.go` only concatenates static SQL fragments, with all user values passed as bound args.
- **Secret leakage in VCS:** `.env` is git-ignored and not tracked; only `.env.example` is committed.
- **Password exposure:** `User.Password` is tagged `json:"-"`.
- **CRUD IDOR:** account, transaction, category, and budget reads/writes are all scoped with `WHERE "userId" = ?` (e.g. `transaction/service.go:146`, `account/service.go:44`).

## Findings

### H-1 — CSV import-job status endpoint lacks ownership check (IDOR)

- **Severity:** High
- **CWE:** CWE-639 (Authorization Bypass Through User-Controlled Key)
- **Location:** `internal/transaction/handler.go:358` (`getImportJob`)

**Description**

`POST /transactions/import` starts a background import scoped to the caller and returns a random `jobId`. The status endpoint `GET /transactions/import/jobs/:jobId` looks the job up purely by `jobId` and never verifies that the job belongs to the authenticated user:

```go
func (h *Handler) getImportJob(c *gin.Context) {
    jobId := c.Param("jobId")
    raw, ok := h.jobs.Load(jobId)   // no CurrentUser(c), no ownership check
    ...
    c.JSON(200, ImportJobStatus{Status: job.status, Result: job.result, Error: job.errMsg})
}
```

The returned `ImportResult` can include imported/failed row detail derived from another user's uploaded file. The `jobId` is a random UUIDv4, so this is not trivially guessable, but there is no authorization binding at all — any leaked, logged, or brute-forced ID exposes another tenant's import outcome. The job map is also process-global and shared across all users.

**Reproduce steps**

1. Authenticate as user A and start an import:
   ```bash
   curl -s -X POST http://localhost:3000/transactions/import \
     -H "Authorization: Bearer <A_TOKEN>" \
     -F "file=@transactions.csv" -F "categoryMapping={}"
   # → {"jobId":"<UUID>"}
   ```
2. Authenticate as an unrelated user B and request A's job with B's token:
   ```bash
   curl -s http://localhost:3000/transactions/import/jobs/<UUID> \
     -H "Authorization: Bearer <B_TOKEN>"
   ```
3. Observe that B receives A's job status and result payload — the request is not rejected as 403/404 for a non-owner.

**Remediation**

Store the owner `userId` in `importJobState` at creation time and reject requests where `job.userId != CurrentUser(c).Sub` with a 404 (to avoid confirming existence). Alternatively key jobs by `(userId, jobId)`.

### H-2 — No rate limiting on authentication endpoints

- **Severity:** High
- **CWE:** CWE-307 (Improper Restriction of Excessive Authentication Attempts)
- **Location:** `internal/auth/handler.go:19` (routes), `cmd/main.go:98-105` (middleware stack)

**Description**

The router uses `gin.Default()` (logger + recovery) plus CORS, with no rate-limiting or lockout middleware. `POST /auth/login` and `POST /auth/register` are therefore open to unlimited automated attempts, enabling password brute force, credential stuffing, and mass account enumeration. bcrypt on login provides some per-attempt cost but does not bound attempt volume.

**Reproduce steps**

1. Run repeated login attempts against one account:
   ```bash
   for i in $(seq 1 500); do
     curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:3000/auth/login \
       -H "Content-Type: application/json" \
       -d '{"email":"victim@example.com","password":"guess'"$i"'"}'
   done
   ```
2. Observe every request is processed and returns `401` with no throttling, `429`, or temporary lockout after a threshold.

**Remediation**

Add per-IP and per-account rate limiting / exponential backoff on `/auth/*` (e.g. a token-bucket middleware or a reverse-proxy rule), and account lockout or CAPTCHA after repeated failures.

### M-1 — Database connection forces `sslmode=disable`

- **Severity:** Medium
- **CWE:** CWE-319 (Cleartext Transmission of Sensitive Information)
- **Location:** `internal/config/config.go:33-38` (`DatabaseConfig.DSN`)

**Description**

The DSN hardcodes `sslmode=disable`:

```go
return fmt.Sprintf(
    "host=%s port=%d user=%s password=%s dbname=%s sslmode=disable",
    d.Host, d.Port, d.User, d.Password, d.Name,
)
```

If the database is on a different host than the API (typical in production), all traffic — including the DB password and every user's financial records — travels unencrypted and is exposed to network eavesdropping / MITM. It is acceptable for the local Docker setup but unsafe as a fixed value.

**Reproduce steps**

1. Deploy with the API and PostgreSQL on separate hosts.
2. Capture traffic on the DB port (e.g. `tcpdump -A -i any port 5432`).
3. Observe the startup authentication and query payloads are readable in cleartext.

**Remediation**

Make `sslmode` configurable via env (default `require` or stronger in non-local environments); reserve `disable` for local development only.

### M-2 — CORS allows all origins

- **Severity:** Medium
- **CWE:** CWE-942 (Permissive Cross-domain Policy)
- **Location:** `cmd/main.go:100-105`

**Description**

```go
r.Use(cors.New(cors.Config{
    AllowAllOrigins: true,
    AllowMethods:    []string{"GET","POST","PUT","PATCH","DELETE","OPTIONS"},
    AllowHeaders:    []string{"Origin","Content-Type","Authorization"},
    ...
}))
```

Any website can call the API from a browser. Because authentication is via a bearer token in the `Authorization` header (not cookies), a malicious origin cannot silently ride an existing session, so the practical impact is limited. It nonetheless removes a defense-in-depth boundary and would become directly exploitable if cookie-based auth is ever introduced.

**Reproduce steps**

1. From a page on an arbitrary origin, issue `fetch("http://localhost:3000/health")` (or any endpoint) and inspect the response headers.
2. Observe `Access-Control-Allow-Origin` reflects/allows the foreign origin.

**Remediation**

Replace `AllowAllOrigins: true` with an explicit allow-list of trusted front-end origins, sourced from config.

### M-3 — User enumeration via registration and timing

- **Severity:** Medium
- **CWE:** CWE-204 (Observable Response Discrepancy)
- **Location:** `internal/auth/service.go:30-31` (register), `internal/auth/service.go:49-62` (login)

**Description**

Registration returns a distinct `409 "Email already in use"` when an address exists, letting an attacker confirm which emails are registered. Login correctly returns a generic `401 "Invalid credentials"` for both unknown users and wrong passwords, but bcrypt only runs when the user exists (`ValidateUser` returns early on `u == nil` before `CompareHashAndPassword`), so response timing differs measurably between existing and non-existing accounts — a second enumeration channel. Combined with H-2 (no rate limiting), an attacker can enumerate the user base at scale.

**Reproduce steps**

1. Enumeration via registration:
   ```bash
   curl -s -X POST http://localhost:3000/auth/register \
     -H "Content-Type: application/json" \
     -d '{"email":"known@example.com","password":"password123"}'
   # 409 "Email already in use" → account exists; 201 → it did not
   ```
2. Timing channel via login: measure latency of `POST /auth/login` for a known-existing email vs. a random non-existent one and observe the existing account is consistently slower (bcrypt executes).

**Remediation**

Return a generic success-style message for registration of an existing email (or send a verification email out-of-band without confirming existence). For login, perform a dummy bcrypt comparison against a constant hash when the user is not found to equalize timing.

### M-4 — No JWT secret strength enforcement

- **Severity:** Medium
- **CWE:** CWE-521 (Weak Password Requirements) / CWE-326 (Inadequate Encryption Strength)
- **Location:** `internal/config/config.go:50-53`

**Description**

Config requires `JWT_SECRET` to be non-empty but imposes no minimum length or entropy. HS256 tokens are only as strong as this secret; a short or low-entropy value can be brute-forced offline against any captured token, allowing an attacker to forge tokens for any `sub` and fully impersonate users.

**Reproduce steps**

1. Set `JWT_SECRET=secret` and start the API — it boots without complaint.
2. Capture any issued JWT and run an offline HS256 cracker (e.g. `hashcat -m 16500`) with a wordlist; a weak secret is recovered quickly, after which arbitrary valid tokens can be minted.

**Remediation**

Enforce a minimum secret length (≥32 bytes) at startup and fail fast otherwise; document generating it from a CSPRNG.

### L-1 — Raw internal error text exposed in import-job status

- **Severity:** Low
- **CWE:** CWE-209 (Generation of Error Message Containing Sensitive Information)
- **Location:** `internal/transaction/handler.go:338` and `:373`

**Description**

On import failure the handler stores `job.errMsg = err.Error()` and returns it verbatim in the status response. If `ImportFromCsv` surfaces a wrapped database or driver error, internal details (SQL fragments, schema/column names) can leak to the client. Elsewhere the app deliberately funnels non-`AppError` errors through the generic `RespondInternalError`; this path bypasses that.

**Reproduce steps**

1. Trigger an import that fails at the DB layer (e.g. force a constraint violation via crafted CSV rows).
2. Poll `GET /transactions/import/jobs/{jobId}` and observe the `error` field contains raw driver/DB text rather than a generic message.

**Remediation**

Return a generic failure message to clients and log the detailed error server-side; only expose `AppError` messages.

### L-2 — Import jobs stored in an unbounded in-memory map

- **Severity:** Low
- **CWE:** CWE-401 (Missing Release of Memory) / CWE-400 (Uncontrolled Resource Consumption)
- **Location:** `internal/transaction/handler.go:40` (`jobs sync.Map`), populated at `:325`

**Description**

Every import creates a job entry that is never deleted. Over time, or under deliberate abuse (repeated small imports), the map grows without bound, leaking memory. Jobs are also lost on restart with no persistence, and shared process-globally (see H-1).

**Reproduce steps**

1. Submit many import requests in a loop and observe process RSS grows monotonically with no eviction.

**Remediation**

Expire/evict completed jobs after a TTL (e.g. a janitor goroutine or a size-bounded cache), and consider persisting job state if durability is needed.

### L-3 — Weak password policy

- **Severity:** Low
- **CWE:** CWE-521 (Weak Password Requirements)
- **Location:** `internal/auth/dto.go:5` (`min=6`)

**Description**

Registration only requires a 6-character password with no complexity or breach-list check, making accounts easier to compromise via guessing (amplified by H-2).

**Reproduce steps**

1. `POST /auth/register` with `"password":"123456"` succeeds with `201`.

**Remediation**

Raise the minimum length (≥8–12) and consider checking against known-breached passwords.

---

### L-4 — No token revocation / logout mechanism

- **Severity:** Low
- **CWE:** CWE-613 (Insufficient Session Expiration)
- **Location:** `internal/auth/service.go:65-81`, `internal/middleware/auth.go`

**Description**

JWTs are stateless with a default 1-hour expiry and no revocation list or logout endpoint. A leaked token remains valid until it expires, and there is no way to invalidate sessions after password change or compromise.

**Reproduce steps**

1. Log in and capture a token; keep using it after "logging out" client-side — it remains accepted until `exp`.

**Remediation**

Keep short expiries; if stronger control is needed, add a revocation/denylist (e.g. Redis) checked in the auth middleware, and invalidate tokens on password change.

---

### I-1 — Swagger UI served without authentication

- **Severity:** Informational
- **Location:** `cmd/main.go:110`

`GET /swagger/*any` is public, exposing the full API surface. Acceptable for internal/dev builds; disable or gate it in production to reduce reconnaissance value.

---

### I-2 — bcrypt cost fixed at 10

- **Severity:** Informational
- **Location:** `internal/auth/service.go:13`

Cost 10 is acceptable today but on the low end. Consider 12 and make it configurable so it can be raised as hardware improves.

## Recommended Priority

1. **H-1** — add ownership check to the import-job endpoint (small, high-value fix).
2. **H-2** — introduce auth rate limiting / lockout.
3. **M-1 / M-4** — make `sslmode` and JWT-secret strength environment-safe before any production deploy.
4. **M-2 / M-3** — restrict CORS and close enumeration channels.
5. Address Low/Info items as hardening.

## Positive Observations

- Parameterized SQL everywhere — no injection surface found.
- Consistent per-user scoping in CRUD services prevents cross-tenant access.
- Passwords bcrypt-hashed and excluded from JSON output.
- Secrets kept out of version control (`.env` git-ignored).
- JWT signing-method is pinned to HMAC in the middleware, preventing `alg` confusion / `none` attacks.
- CSV upload enforces a 10 MB limit and content-type/extension check.
